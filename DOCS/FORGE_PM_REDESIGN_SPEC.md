# The Forge — PM Tool Redesign Spec

**Version:** 1.0.0
**Date:** 2026-10-30
**Status:** Planning — not yet in development
**Author:** Marc Yap + Claude Sonnet 4.6

---

## 1. Vision

The Forge stops being a coding agent and becomes a **professional AI product manager** for non-coders building apps and AI products.

It does not write code. It understands what exists, tracks what needs to be built, generates the artefacts a real software engineer would produce, and hands the user a ready-to-run prompt for Claude Code. The user pastes the prompt, Claude Code builds the feature, and The Forge records what shipped.

**The core loop:**
```
Repo changes → Forge re-scans → updates feature map + architecture
User picks a feature → Forge generates Claude Code prompt + acceptance criteria
User runs prompt in Claude Code → feature ships
User marks done → Forge records it, updates architecture + changelog
```

---

## 2. User Persona

**Marc** — non-coder building apps and AI products professionally. Needs to operate at the standard of a real software engineer: structured planning, tracked decisions, clean architecture, quality gates, and auditable records — without writing code himself.

The Forge gives him the scaffolding a senior engineer carries in their head.

## 4. Feature Set

### 4.1 Prompt Generator
The primary new feature. Select any feature on the Kanban board → tap "Generate Prompt" → The Forge:
1. Reads the relevant repo files (scoped to files related to the feature)
2. Generates acceptance criteria (what done looks like, edge cases, test requirements)
3. Writes a tight Claude Code implementation prompt including: context, files in scope, exact change description, definition of done, gotchas
4. Stores the prompt as `.forge/prompts/<feature-id>/<date>.md`
5. Presents it with a "Copy to clipboard" button

The prompt always includes:
- Security checklist items relevant to the change
- File paths and line number hints where known
- A "do not touch" list (files outside scope)
- The acceptance criteria as a testable checklist

### 4.2 Prompt Tracker
Per-feature history of every generated prompt: date, status (generated / used / shipped / abandoned), link to the resulting checkin record. Visible as a tab on the feature detail panel. Allows re-opening and re-using any past prompt.

### 4.3 Architecture View
A live Mermaid diagram of the linked repo's structure — components, data flow, key dependencies. Generated by LLM reading the codebase. Rendered in a WebView panel using locally bundled Mermaid.js.

- Stored as `.forge/architecture/ARCHITECTURE.mmd`
- Regenerated on repo sync (debounced — not on every save)
- Component map: which files belong to which feature/subsystem
- Clicking a component shows which features touch it
- "Regenerate" button for on-demand refresh

### 4.4 Architecture Decision Records (ADRs)
Permanent record of *why* structural decisions were made. Generated by the user triggering "Log a decision" or automatically prompted when the Forge detects a significant architectural change (new subsystem, dependency added, pattern change).

Each ADR contains: decision title, date, context, options considered, decision made, consequences. Stored as `.forge/adrs/ADR-NNN-<slug>.md`. Listed in the ArtifactViewerScreen with a dedicated ADR panel.

### 4.5 Health Dashboard
Signals that the repo needs attention — without requiring the user to run commands.

- **Linter** — last known `dart analyze` result (clean / N warnings / N errors)
- **Tests** — last known `flutter test` result (N passed / N failed)
- **File size warnings** — files approaching or exceeding architecture line-count limits
- **Dependency staleness** — packages with available updates
- **Architecture drift** — files that have grown significantly since last architecture snapshot

Populated by reading `.forge/` logs from Claude Code sessions. The Forge does not run these commands itself.

### 4.6 Acceptance Criteria Generator
Before generating a prompt, The Forge automatically generates acceptance criteria for the feature: user-facing behaviour, edge cases, security considerations, and a testable checklist. Presented to the user for review before the prompt is created. Saved alongside the prompt record.

### 4.7 Impact Analysis
Before generating a prompt, The Forge scans the repo and reports which existing files and features the proposed change is likely to affect. Prevents partial integrations (the BUG-IMPL-015 class of failure). Presented as a "This build touches X files across Y features — review before prompting" summary.

### 4.8 Session Starter Generator
Generates a context brief for a new Claude Code session: current architecture state, last session's changes, the feature being built, relevant file paths, and any known gotchas. The user pastes this at the start of every Claude Code session instead of re-explaining context from scratch.

Stored as `.forge/session_starters/<date>-<feature-slug>.md`.

### 4.9 Release Notes Generator
After a feature or batch of features ships, generates plain-English release notes: what was built, why it matters, what changed technically. Two versions: stakeholder-facing (no code) and technical (file-level). Stored as `.forge/releases/v<N>-<date>.md`.

### 4.10 Product Sense Advisor
Periodic analysis of the repo + feature board that answers: "What's missing? What's inconsistent? What would a senior engineer do next?" Surfaces gaps, architectural risks, features that depend on unbuilt infrastructure, and quality debt. Not prescriptive — advisory only.

## 5. LLM Roles (new set)

| Role | Trigger | What it does |
|---|---|---|
| **FeatureScanner** | Repo sync | Reads codebase, identifies/updates feature list |
| **PromptWriter** | "Generate Prompt" tap | Reads relevant files, writes Claude Code prompt + acceptance criteria |
| **ArchitectureAnalyst** | Repo sync / on-demand | Generates Mermaid diagram + component map |
| **ImpactAnalyst** | Before prompt generation | Reports which files/features a proposed change touches |
| **ADRWriter** | User-triggered / structural change detected | Writes architecture decision record |
| **ReleaseNotesWriter** | Feature marked shipped | Writes plain-English release notes |
| **ProductAdvisor** | Weekly / on-demand | Reviews repo + board, surfaces gaps and next steps |

All roles receive only the files and context they need — no generation history, no cross-role bleed. Each call is short and focused; token cost per action is a fraction of an executor build loop.

## 6. Generated Artefacts — File Structure

```
.forge/
├── prompts/
│   └── <feature-id>/
│       └── <date>.md          ← generated Claude Code prompt
├── architecture/
│   ├── ARCHITECTURE.mmd       ← current Mermaid diagram
│   └── component_map.json     ← files ↔ features mapping
├── adrs/
│   └── ADR-NNN-<slug>.md      ← architecture decision records
├── session_starters/
│   └── <date>-<feature>.md    ← Claude Code session context briefs
├── releases/
│   └── v<N>-<date>.md         ← release notes
├── acceptance_criteria/
│   └── <feature-id>.md        ← acceptance criteria per feature
└── checkins/                  ← existing — post-ship records
```

All artefacts are plain Markdown or JSON. They are readable without The Forge. They are committed to the repo's workspace, not locked in a database.

## 7. Out of Scope (this redesign)

- Code execution of any kind
- Running `dart analyze` or `flutter test` directly
- Any build-with-AI capability
- iOS/Android deployment
- Multi-user collaboration
- Web or mobile version of The Forge

## 8. Phased Build Plan

### Phase 1 — Strip the executor (1 session)
**Goal:** The Forge runs cleanly with no executor code. Tracker, settings, watch, and LLM service all work.

**Work:**
- Delete `lib/features/implementation/` and `lib/features/run/`
- Remove `InspectorService`, `BuildAdviceScreen`, `ImplBrief`
- Remove Scout sub-role from `LlmService`
- Fix all broken imports and references
- Replace "Build" button in `ProjectTrackerScreen` with disabled "Prompt (coming soon)" placeholder
- `dart analyze` clean, all remaining tests pass

**Definition of done:** The Forge launches, the Kanban board works, no executor code remains, analyze is clean.

---

### Phase 2 — Prompt Generator + Tracker (2 sessions)
**Goal:** User can select a feature and get a Claude Code prompt with acceptance criteria, stored and retrievable.

**Work:**
- Add `PromptWriter` LLM role
- Add `PromptRecord` drift table (featureId, date, promptPath, status)
- Add `ImpactAnalyst` LLM role (runs before prompt generation)
- Add `AcceptanceCriteriaGenerator` LLM role (runs before prompt generation)
- New UI: feature detail panel → "Generate Prompt" → acceptance criteria review → prompt display → copy button
- Prompt Tracker tab on feature panel (history)
- Save artefacts to `.forge/prompts/` and `.forge/acceptance_criteria/`

**Definition of done:** Tapping "Generate Prompt" on any feature produces a copyable Claude Code prompt with acceptance criteria and impact summary. Prompt is stored and retrievable.

---

### Phase 3 — Architecture View (2 sessions)
**Goal:** Live Mermaid architecture diagram always accessible in the app.

**Work:**
- Add `ArchitectureAnalyst` LLM role
- Bundle Mermaid.js as a Flutter asset
- Add `webview_flutter` dependency
- Architecture panel in `ProjectTrackerScreen` (side panel or dedicated screen)
- Component map: files ↔ features linkage
- Repo sync triggers architecture regeneration (debounced 30s)
- Save `.forge/architecture/ARCHITECTURE.mmd` + `component_map.json`

**Definition of done:** Architecture panel shows a rendered Mermaid diagram of the linked repo, regenerates on repo changes, component map is accurate.

---

### Phase 4 — Health Dashboard + ADRs + Session Starter (2 sessions)
**Goal:** User always knows the repo's health state and has a session context brief ready before opening Claude Code.

**Work:**
- Health Dashboard panel: reads `.forge/` logs + last-known analyze/test results
- File size and dependency staleness signals
- `ADRWriter` LLM role + ADR panel in ArtifactViewerScreen
- "Log a decision" button on architecture view
- `Session Starter Generator`: one tap → context brief for next Claude Code session
- Save to `.forge/session_starters/`

**Definition of done:** Health panel shows meaningful repo signals. User can generate an ADR. "Start session" button produces a Claude Code context brief.

---

### Phase 5 — Release Notes + Product Advisor (1–2 sessions)
**Goal:** The Forge tells you what shipped and what to build next.

**Work:**
- `ReleaseNotesWriter` LLM role — triggered when features marked shipped
- Release notes panel + save to `.forge/releases/`
- `ProductAdvisor` LLM role — weekly digest + on-demand query
- "What should I build next?" button in ProjectTrackerScreen

**Definition of done:** Marking a feature shipped generates release notes. "What next?" produces a ranked list of recommendations with reasoning.

---

## 9. Success Criteria

The redesign is complete when Marc can:
1. Open The Forge, see the health of any linked repo at a glance
2. Pick any feature and get a production-quality Claude Code prompt in under 30 seconds
3. See the current architecture diagram without opening any file
4. Know why every structural decision was made (ADR trail)
5. Start any Claude Code session with a context brief that takes 10 seconds to generate
6. Read plain-English release notes for anything that shipped
7. Ask "what should I build next?" and get a grounded, reasoned answer
